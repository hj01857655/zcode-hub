## 0. 一页结论

核心链路（quota 双通道、`is_empty` 双看、版本头策略、touch 解析、1004 不重试、切换的 hash/identity/auto_preserve/hot 双读校验）**与实测结论一致，均已落地**。发现 3 个值得改的点：① ~~`claim_refresh` 仍在补报激活事件~~（**2026-11-03 已修**，见 §2.1）；② auto claim 验证码取票无重试；③ quota 与 claim 两套身份策略矛盾（quota 用全局 live mid，claim 用 per-account virtual mid）。另 hot 切换漏写 `providerFamilyDomain`、preview 死通道、popup 投放不解析三个小项。

## 2. 建议修改（按优先级）

### 2.1 ✅ `claim_refresh` 补报激活事件 —— 已删除（2026-11-03）

原状：每次 `claim_refresh` 调 `claim::report_activation_events` 发 `app_launch` + `app_daily_active` 两条。50 §2.5 的决定性实验已证**零因果**（零上报新号直达 touch 投放并 claim 成功），claim_check.js 侧早已移除。

问题不止是多余——**节奏对不上官方指纹**（59 §9.1）：官方 `app_daily_active` 有 `lastDailyActiveDate` 日级去重，**每设备每天至多 1 条**；`app_launch` 只在启动时发。而 auto claim 开着时每 10 分钟对每号发 2 条 → 一个号一天最多 288 条。`screen_resolution` 还硬编码 `"2560x1440"`。

**落地**：整条上报链路删除 —— `report_activation_events` / `activation_event_body` / `device_os_category` / `EVENT_REPORT_URL` / `ACTIVATION_EVENTS` / `SCREEN_RESOLUTION` 与 `err.claim.activate_req` 文案全清；`claim_refresh` 命令本身去掉（去掉上报后与 `claim_preview` 逐字节等价），前端三处调用点（auto 批量 / 手动批量 / 单号）改直连 `claim_preview`，`ClaimRefreshResult.activated/activation_error` 连带删除。`telemetry_user_id` 保留为 `oauth_user_id`（`store.rs:1535` 的 `has_user_info` 依赖它）。UI 文案「激活资格」改「刷新资格」。

### 2.2 quota 与 claim 两套身份策略矛盾（设计级不一致）

claim 链路：每号一个 `virtual_device_mid`，claim/touch 全带账号自己的 mid（lib.rs:262 → claim.rs）。quota 链路：`zai_billing_headers()` 走 `device_mid()`（quota.rs:189-191），读的是**全局 telemetry-state.json 的 live mid**——即「当前激活号」的 mid。结果给全部账号刷额度时，服务端看到 A 号 JWT 配 B 号 mid，且所有号共享同一 mid。

服务端对 balance 是否容忍 mid 错配**未实测**。两套策略并存说不通：要么 quota 也走 per-account mid，要么实测证明错配无风险（那 claim 侧的讲究也失去意义）。

### 2.3 auto claim 验证码无重试：无痕失败即弃轮

auto 模式走 `captcha.html` 无痕验证（captcha.js:110-124），`startTracelessVerification` 8 秒（`TRACELESS_TIMEOUT`）不成功即转 interactive；auto 窗口 hidden，用户看不见，`waitForClaimResult` 45s 超时 → cancel → 10 分钟冷却（store.js:246-251）。工具链 `captcha_solve.js` 实测无痕成功率 ≈1/2（靠 3 次重试兜底），应用内**一次失败就整轮放弃**。

**建议**：auto 模式无痕失败自动重载 SDK 再试 1-2 次（`location.reload()` 机制已存在，lib.rs:843-850）；或 interactive 转出时短暂弹窗提示手动点（当前 hidden + 超时 = 静默丢轮）。

### 2.4 hot 切换跨 provider 漏写 `providerFamilyDomain`

`align_family_domain` 只在冷切换路径调用（store.rs:919），hot 分支（store.rs:858-883）没有。热切换 zai ↔ bigmodel 跨族账号时，credentials.json / config.json 都换新了，setting.json 里的 `providerFamilyDomain` 还是旧账号的域，客户端热加载新身份后路由域仍是上一家的，冷切一次才纠正。

### 2.5 热切换写 telemetry-state.json 的竞态：客户端会用内存旧 mid 整写回

hot 分支 `write_live_device_mid`（store.rs:869）在客户端**运行中**执行。客户端 `ensureDeviceMidInLockedState` 启动时读一次进内存（60 §2），后续心跳落盘 `lastDailyActiveDate` 会把**内存里的旧 mid 原样写回**——切换器的写入被覆盖，运行会话继续旧 mid + 新 JWT。「设备身份跟账号走」在热切换下不成立。

旁证：already 分支 arms uid 写入有 `if !zcode_running()` 守卫（store.rs:841-843），deviceMid 写入没有——同一对文件一个防了竞态一个没防。要么热切换下两个都不写（冷启自然生效），要么都写并接受覆盖，当前是中间态。

### 2.6 preview 死通道仍占主路径

50 §3 实测 preview **恒空**（不是偶发坏），`preview_plans` 每次仍先打 preview（claim.rs:235），三个调用点各多一次死请求。现状是 preview=空并集、touch=唯一来源，注释「preview 只是副通道」已过时。**建议**：降为 debug/env 可选项或删，注释改口径。

### 2.7 popup 型投放不解析

`touch_plans` 只扫 `deliveries[].banner.buttons`（claim.rs:297-315）。60 §3 schema：`resource_position` 是 `"banner" | "popup"` 双型 union，**popup 同样带 buttons、同样可有 `claim_zcode_plan`**。野外至今只见 banner，但服务端一旦用 popup 投领取卡会静默漏掉。**建议**：按钮扫描放宽到顶层 `buttons ∪ banner.buttons`，成本三行。

## 3. 边界备忘（不改也行）

- **claim 的 token 兜底**：`claim_token` 优先 zcodejwttoken，无则 `zai_billing_token`——active=bigmodel 且无 start-plan key 的号直接报 `no_jwt`。真实账号库中不存在此形态，记录备查。
- **fetch_captcha_config 空 Bearer**（claim.rs:443）：`client/configs` 无鉴权可调，官方带 token；行为差异无风险。**同源影响面（2026-10-31 补）**：聊天链路与 claim 共用同一份 `captcha` 配置——host 闸门 `j7 requiresRequestVerification`（`enabled!==false && skip_model_request!==true` 才对 messages 预检取票），实测当前 `skip_model_request: true` 即模型请求豁免、chat 可裸打；豁免是服务端一行配置，翻 `false` 后一切第三方 chat 请求会撞 3007/「请完成安全验证」挑战，届时需在 messages 请求头附 claim.rs:416 同款 `X-Aliyun-Captcha-Verify-Param`（管道详见 [08 §1.2](../../docs/zcode-plan-08-聊天对话接口.md)、[12 §1/§3/§4](../../docs/zcode-plan-12-阿里云验证码体系.md)）。
- **多号共享出口 IP**：auto claim 每轮 4 请求/号，mid 全部走 per-account virtual mid（服务端视角 N 个独立设备），工具固有形态，仅记录。
- **阻塞 IO 在 async command 里**：`get_live_quota` 等 tauri async command 直接调同步 ureq + sleep（lib.rs:250-257、quota.rs:387-443），多号刷新占死 runtime 线程，该 `spawn_blocking`。代码质量级。
- 1005 的 `next_at` 取 `data.plan.ends_at`（claim.rs:71-77）：响应带该字段才有意义，取不到即空，无错误路径。

## 4. 验证说明

本审查只做了源码通读与逆向文档对照，**没有**编译运行本工具、没有抓真实请求验证头序/节奏。§1「已落地」以代码为准；§2.1 的节奏指纹分析基于 59 号实测的官方行为与 store.js 常量的算术推算；§2.2/§2.5 的服务端容忍度与竞态后果未实测。~~若要闭环 §2.1：看 `~/.zcode/v2/logs/` 的 event/report 频次对照~~ —— **此法无效（2026-11-03 实测）**：`~/.zcode/v2/logs/` 是 ZCode 自己的 host 日志，一是本工具是独立进程，它的 ureq 请求不会落进这里；二是官方 `sendReport` 在 main 进程直连 fetch，同样不走打日志的 host RPC 通道 —— 当天日志里 `event/report` / `app_daily_active` / `app_launch` 全 0 命中（654 处 `event_id` 全是 `[mobile-push]` 的会话事件，555 处 `marketing-touch` 才是走 host RPC 会被记录的），即客户端在跑也留不下痕迹。§2.1 的闭环只能靠对 `zcode-switch` 进程抓包，或以代码为准（`EVENT_REPORT_URL` 字符串已从整个 `src-tauri` 消失）。

## 5. 2026-11-03 复核与补修（关闭剩余条目）

v1.9.1 逐条核对 + 本轮补修，原 7 条建议**全部关闭**：2.2 / 2.4 / 2.5 在 v1.9.1 前已落地（quota 全链显式传 mid、`align_family_domain` hot/cold 两分支均调、三处 `write_live_device_mid` 加 `if !zcode_running()` 守卫），2.1 见 §2.1，本轮再补三条。

### 2.3 ✅ 验证码无痕失败重试

`open_captcha_window` 把模式随 URL 传下（`captcha.html?auto=1`；复用窗口改用 `location.replace` 而非 `location.reload`，否则手动流程转 auto 会带上一次的 query 而丢掉重试能力）。`captcha.js` 仅在 auto（隐藏窗）模式下经 `retryOrFail` 重推 `startTracelessVerification`，最多 2 次 —— 3 轮 × 8s = 24s，落在 `AUTO_CLAIM_WAIT_MS` 45s 预算内；`fail` / `onError` 同走这条路径（原先两处直接 `interactive`）。手动模式**不重试**：用户对着弹窗干等 24 秒不如立刻看到按钮。新增文案 `c.tracelessRetry`（zh/en 各一条，`check:i18n` 键数 468 → 469）。

无痕成功率 ≈1/2 是工具链 `captcha_solve.js` 的实测值，单次尝试 ≈50%、3 次内成功 ≈87.5% —— 这是推算，未在应用内实测。

### 2.6 ✅ preview 降为可选通道

`preview_plans` 主路径不再打 `billing/preview`：50 §3 实测恒空，且该端点已知会 429，每次刷新白送一个必死请求。置 `ZSW_CLAIM_PREVIEW` 环境变量可恢复副通道（行为与原先一致：失败不连坐、非空则补全 touch 条目），与仓库既有先例同款（`ZSW_DUMP_SUB`、`ZCODE_GATEWAY_APP_VERSION`）。注释口径改为「投放是唯一来源，preview 仅供归因对照」。

调用点也从三个降到两个（`claim_preview` / `claim_start`）—— §2.1 删 `claim_refresh` 时顺带带走了第三个。

### 2.7 ✅ popup 型投放解析

`touch_plans` 的按钮扫描从只读 `d.pointer("/banner/buttons")` 改为遍历 `[d.get("banner"), Some(d)]` 并集去重，`zcode_plan` 取路从 2 条扩到 4 条（`/banner/background/{args,bundle/args}/zcode_plan` 加无 `banner` 前缀的同名两条）。60 §3 的 `resource_position: "banner" | "popup"` 双型里，原先 popup 会走 `wanted.is_empty() → continue` 静默漏掉。

**未验证**：野外至今只见 banner 型投放，本条属前向兼容改动，没有真实 popup 样本可跑。
